The semantic pass is basically the moment when the code has already passed the lexer and parser, and the AST has been built. Then the AST is checked for correctness and whether the code itself makes sense. For example, it checks whether types are correct, whether variables are declared before use, and whether a `keep` variable, which is immutable, is not changed later in the program.

A mutability chain means that when we want to change a nested field, every part of the path to that field must be mutable. For example, in `c.center.x <- 5`, `c`, `center`, and `x` must all allow mutation. If one part of the chain is immutable, the assignment is not allowed. A member function is mutating if it changes a field of its object, or if it calls another mutating member function. Such a function can only be called on a mutable object and through a fully mutable chain.

The backend uses `llvmlite.ir` instead of building LLVM text manually because it helps to build structurally valid LLVM IR using actual LLVM values, types, blocks, and instructions.

If overflow can already be detected from literal expressions, for example `2147483647 + 1`, FaceCard reports a compilation error.

If a value comes from `draw()`, the result is not known during compilation. In our implementation, the generated LLVM code checks for overflow at runtime and terminates the program with `abort()` instead of silently producing an incorrect wrapped value. так ок ? можемо додавати?

4. What I understood
I supplied the explanation below in this conversation after discussing the
implementation with AI. I accepted one clarification about mutation on the
same object or its fields and an AI-written addition about string storage.
The explanation and its wording are therefore also AI-assisted.

The semantic pass is basically the moment when the code has already passed
the lexer and parser, and the AST has been built. Then the AST is checked for
correctness and whether the code itself makes sense. For example, it checks
whether types are correct, whether variables are declared before use, and
whether a `keep` variable, which is immutable, is not changed later in the
program.

A mutability chain means that when we want to change a nested field, every
part of the path to that field must be mutable. For example, in
`c.center.x <- 5`, `c`, `center`, and `x` must all allow mutation. If one part
of the chain is immutable, the assignment is not allowed. A member function
is mutating if it changes a field of its own object, or calls another mutating
member function on the same object or one of its fields. Such a function can
only be called on a mutable object and through a fully mutable chain.

The backend uses `llvmlite.ir` instead of building LLVM text manually because
it helps to build structurally valid LLVM IR using actual LLVM values, types,
blocks, and instructions.

If overflow can already be detected from literal expressions, for example
`2147483647 + 1`, FaceCard reports a compilation error.

If a value comes from `draw()`, the result is not known during compilation.
In our implementation, the generated LLVM code checks for overflow at runtime
and terminates the program with `abort()` instead of silently producing an
incorrect wrapped value.

In FaceCard, a string value is a pointer to a null-terminated global UTF-8
constant. Assignment copies the pointer, and the constant remains available
throughout program execution. Since this stage does not create strings
dynamically, it does not need dynamic allocation or garbage collection.
